# M20 — Optional AI Content Remediation + JSON-LD Guidance

**Status:** APPROVED FOR IMPLEMENTATION  
**Identifier:** `M20`  
**Dependency:** M18 + SCORE-GEO-002 + REPORT-SITE-GEO-001

## 1. Objective

M20 adds an optional, downstream remediation layer that may propose exact website copy for evidence-backed content/semantic findings and may provide deterministic JSON-LD guidance per audited page/device.

M20 is **not** a scoring stage. It must never alter retrospectively:

- `RuleExecution`;
- `Finding`;
- `Recommendation` generated by M10;
- Score;
- Coverage;
- Confidence;
- Consolidation.

All M20 output is advisory and requires human review before publication.

## 2. Default and activation

Textual remediation by external AI is OFF by default.

Public controls:

```text
--ai-content-remediation
--no-ai-content-remediation
SEARCHGEO_AI_CONTENT_REMEDIATION
```

Precedence:

1. explicit CLI boolean flag;
2. environment variable;
3. `false`.

Accepted environment values are `true/false`, `1/0`, `yes/no`, `on/off` case-insensitively.

JSON-LD guidance is deterministic and remains available even when textual AI remediation is disabled or no AI provider is configured.

## 3. Trigger contract

Textual M20 must be triggered only by eligible persisted content/semantic findings.

`Confidence LOW` by itself is **never** a trigger and must not be interpreted as poor content.

Eligible rule universe for exact-text proposals in this version:

```text
BR-GEO-028..033
BR-GEO-038..049
```

Structured-data rules are not sent to the free-form content remediation prompt. JSON-LD guidance is handled separately under the deterministic contract in this specification.

## 4. Evidence boundary

Each external M20 request is scoped to one persisted page snapshot/device and may contain only:

- normalized page URL;
- selected device;
- observed title;
- bounded persisted main-content artifact;
- eligible findings for that page/device;
- expected condition and observed value of those findings;
- persisted evidence linked to those findings.

Provider output must reference an existing supplied `finding_id` and evidence IDs that are a subset of that finding's persisted evidence IDs.

A suggestion with foreign or invented finding/evidence references is contract-invalid and must not be published.

## 5. Exact-text output

Each accepted suggestion contains:

- `finding_id`;
- objective of the change;
- target location/placement;
- exact proposed text;
- evidence IDs;
- suggestion confidence;
- mandatory human-review note;
- provider/model persisted separately.

The system must never write the suggestion back into the audited website.

## 6. People-first and anti-fabrication contract

Provider instructions must require content that improves real-user usefulness, clarity, completeness or trust.

M20 must not ask a provider to:

- write only for search engines or generative systems;
- keyword-stuff;
- meet arbitrary word-count targets;
- apply artificial chunking solely for AI retrieval;
- fabricate freshness/date changes;
- invent prices, claims, guarantees, statistics, credentials, expertise, experience or sources;
- generate unsupported mass content.

As a local hardening rule, numeric/date/price-like tokens introduced in proposed copy must already be present in the supplied persisted content/evidence corpus. Otherwise the provider response is rejected as a contract error.

This numeric guard is additive risk containment; it does not prove that every nonnumeric statement is factual. Human review remains mandatory.

## 7. Provider routing

M20 reuses the already configured M18 provider universe. It does not introduce separate credentials or model configuration.

Rules:

1. providers quarantined by M18 for the current audit are not reactivated for M20;
2. explicit provider behavior remains single-provider;
3. AUTO may use the remaining healthy configured chain;
4. calls are sequential;
5. the first valid response stops the chain for that request;
6. provider success establishes URL provider pinning for subsequent M20 contexts of the same URL;
7. a failed provider is quarantined for the M20 routing session;
8. no automatic timeout retry;
9. selected `SEARCHGEO_DEVICE_CONTEXT` bounds the M20 request universe because only selected snapshots exist downstream.

M20 provider failure is an auditor operational state and is never a website finding.

## 8. Telemetry

M20 persists telemetry separately from M18 semantic-analysis attempts so cost by purpose remains auditable.

Minimum telemetry:

- URL;
- page/snapshot/device;
- provider/model;
- reasoning profile;
- attempt index;
- status;
- timestamps/duration;
- sanitized diagnostic class/status/code/request id;
- input/cached/output/reasoning/total tokens when reported;
- locally estimated cost/currency/pricing version;
- request summary/hash;
- M20 contract version.

Raw API keys, Authorization headers and unbounded provider error bodies must never be persisted.

## 9. M20 run states

Persisted run states include:

```text
DISABLED
NOT_CONFIGURED
NO_ELIGIBLE_FINDINGS
SUCCESS
PARTIAL
NO_SAFE_SUGGESTIONS
DEGRADED
```

`NOT_CONFIGURED`, `PARTIAL` and `DEGRADED` do not change website scoring.

## 10. JSON-LD guidance when absent

For each actually audited snapshot/device with no persisted JSON-LD artifact, SearchGEO may materialize a conservative Schema.org `WebPage` baseline using only persisted/observed data.

Permitted generic fields include:

```json
{
  "@context": "https://schema.org",
  "@type": "WebPage",
  "url": "<canonical-or-normalized-url>",
  "inLanguage": "<audit-language>",
  "name": "<observed-title-if-present>",
  "description": "<observed-meta-description-if-present>"
}
```

An optional `mainEntity` may be included only when a single high-confidence persisted entity is sufficiently unambiguous and supported by the visible/persisted page evidence. The auditor must prefer omission over speculative typing.

The baseline must not invent FAQ items, reviews, ratings, prices, authors, dates, offers, addresses, credentials, product identifiers or any other property not supported by observed content.

A generic `WebPage` proposal is not a promise of Google rich-result eligibility.

## 11. JSON-LD guidance when present

When persisted JSON-LD exists, M20 does not replace it wholesale. It performs non-destructive generic review and may identify:

- JSON parse errors;
- identical duplicated blocks;
- absence of a document/graph `@context`;
- nodes missing `@type`;
- a `WebPage` node missing `url`, `name`, `description` or `inLanguage` when the corresponding value is already persisted;
- opportunity to represent page-level `WebPage` semantics without replacing a valid more-specific main type.

When no generic issue is detected, the report must say that type-specific required/recommended properties still need validation against the applicable feature documentation.

## 12. Structured Data external guidance

M20 must communicate all of the following accurately:

- Google supports JSON-LD, Microdata and RDFa and generally recommends JSON-LD for ease of implementation;
- Structured Data must represent content visible/relevant on the page and must not be misleading;
- more-specific applicable Schema.org types are preferable when they faithfully describe the content;
- required/recommended properties vary by Search feature/type;
- valid markup does not guarantee that a rich result will be shown;
- Structured Data/JSON-LD is not a universal requirement for generative Search/GEO;
- SearchGEO must not invent special GEO/AEO markup.

Primary references:

- Google Search Central — General Structured Data Guidelines: `https://developers.google.com/search/docs/appearance/structured-data/sd-policies`
- Google Search Central — Intro to Structured Data: `https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data`
- Schema.org documentation: `https://schema.org/docs/documents.html`
- Google Search Central — Optimizing for generative AI features: `https://developers.google.com/search/docs/fundamentals/ai-optimization-guide`

## 13. Report contract

REPORT-SITE-GEO-001 is extended with:

```text
<AUD-ID>/report/content-suggestions.html
```

The page must show:

- M20 enable/status/counts;
- exact textual suggestions grouped by page/device/finding;
- objective, placement, evidence, provider/model and review requirement;
- JSON-LD proposal when absent;
- JSON-LD improvement notes when present;
- explicit advisory/non-scoring language.

The shared report navigation must expose this page.

M20 telemetry must also be visible in `report/ai-usage.html`, clearly separated from M18 semantic-analysis telemetry.

## 14. Persistence invariants

M20 tables are additive to `audit.db` and must preserve reopenability.

Minimum logical entities:

```text
ContentRemediationRun
ContentRemediationSuggestion
ContentRemediationAttempt
JsonLdRemediationSuggestion
```

Foreign keys must link suggestions to the already persisted audit/page/snapshot/finding universe as applicable.

## 15. Acceptance criteria

M20 is complete only when:

1. default audit makes no additional external content-remediation call;
2. default audit still produces deterministic JSON-LD review;
3. enabled M20 uses only eligible persisted findings/evidence;
4. invalid foreign evidence references are rejected;
5. unsupported numeric claims are rejected;
6. provider failures remain operational, not website findings;
7. M20 does not alter pre-existing score/findings;
8. `mobile`, `desktop`, `both` keep correct device scoping;
9. report site exposes the new page with shared external CSS and no inline style dependency;
10. AI telemetry distinguishes M18 and M20 purposes;
11. unit/integration regression suite passes;
12. real Chromium smoke passes with M20 disabled and with M20 enabled but no provider configured;
13. documentation/CLI/config glossary are aligned;
14. temporary validation workflow is removed before merge.
